# QA Mobile Automation Framework

## О проекте

Проект представляет собой фреймворк для автоматизированного тестирования
мобильного приложения **AlfaBank QApp** с использованием Appium и Java.

Фреймворк организован с расчётом на поддержку Android и iOS. На текущий момент в проекте
реализована Android-часть; iOS-конфигурация и отдельные пакеты под iOS
предусмотрены как основа для дальнейшего расширения.

## Технологический стек

  Технология                 Назначение
  -------------------------- -----------------------------------------------
  Java                       Язык разработки
  Maven                      Сборка проекта и управление зависимостями
  Appium Java Client         Автоматизация мобильного приложения
  Selenium                   WebDriver API и взаимодействие с элементами
  TestNG                     Организация и запуск тестов
  Allure                     Отчёты о выполнении тестов
  Jackson                    Чтение JSON-конфигураций устройств
  SLF4J + Logback            Логирование
  PicoContainer              Управление контекстом/зависимостями сценариев

## Архитектура фреймворка

### Конфигурация

Пакет `config` отвечает за чтение настроек проекта:

-   `ConfigManager` загружает общие параметры из `config/config.properties` и определяет выбранную платформу.
-   `EnvironmentConfig` предоставляет получение обязательных переменных окружения.
-   `DeviceConfig` описывает конфигурацию устройства.
-   `DeviceConfigLoader` загружает список устройств из JSON-файла, соответствующего выбранной платформе.

Платформа выбирается переменной окружения `A_TEST_PLATFORM`. Поддерживаемые значения: `ANDROID` и `IOS`.

### Управление устройствами

`DevicePool` хранит доступные устройства в потокобезопасной блокирующей очереди.

Перед запуском тест получает свободное устройство через`acquireDevice()`. Если свободных устройств нет, 
поток ожидает, пока одно из устройств не будет возвращено в пул. После завершения теста устройство освобождается 
посредством `releaseDevice()`.

`DevicePoolManager` предоставляет общий экземпляр пула устройств.

### Управление Appium-драйвером

Пакет `driver` содержит интерфейс/абстракцию фабрики драйверов и
платформенные реализации:

-   `AndroidDriverFactory` --- создание Android-сессии.
-   `IosDriverFactory` --- предусмотренная точка расширения для iOS.
-   `DriverManager` --- управление экземпляром драйвера в рамках потока.

### UI-слой

UI-слой разделён на экраны и элементы:

-   `BaseScreen` и `Screen` задают общую основу экранов.
-   Android-классы реализуют конкретное взаимодействие с элементами приложения.
-   `BaseElement` содержит общую функциональность UI-элементов.
-   Интерфейсы `Button`, `Label`, `TextField` и `ToggleIcon` задают операции над соответствующими типами элементов.
-   Фабрики экранов и элементов призваны отделить тестовые шаги от платформенной реализации UI.

### Тесты и контекст

`BaseTest` выполняет общую подготовку и завершение теста:

1.  Создаёт уникальный идентификатор теста.
2.  Инициализирует контекст теста.
3.  Получает свободное устройство из пула.
4.  Создаёт Appium-драйвер.
5.  После теста завершает сессию драйвера и возвращает устройство в пул.
6.  Прикрепляет лог выполнения к результатам Allure и очищает контекст.

## Требования к окружению

Для запуска проекта необходимы:

-   JDK 17;
-   Maven;
-   установленный и запущенный Appium Server;
-   Android SDK и Android Emulator;
-   запущенные Android-эмуляторы или подключённые Android-устройства;
-   установленные переменные окружения для выбора платформы и тестовых учётных данных.

Для Android автоматизации также должен быть установлен соответствующий драйвер Appium (UiAutomator2).


## Настройка проекта

### 1. Обязательные переменные окружения

Перед запуском тестов необходимо задать:

  Переменная          Назначение                      Пример
  ----------------- ------------------------------- -----------------
  `A_TEST_PLATFORM`   Выбор платформы                 `ANDROID`
  `A_TEST_LOGIN`      Логин тестового пользователя    `your_login`
  `A_TEST_PASSWORD`   Пароль тестового пользователя   `your_password`

### 2. Общие настройки

Файл `src/test/resources/config/config.properties` содержит общие
параметры:

``` properties
# Appium server
appium.server.url=http://127.0.0.1:4723

# Application
app.package=com.alfabank.qapp

# Timeout
test.timeout.seconds=15
```

Если Appium Server запущен по другому адресу или порту, необходимо
изменить `appium.server.url`.

### 3. Конфигурация устройств

Список Android-устройств задаётся в
`src/test/resources/devices/android.json`.

Список iOS-устройств задаётся в
`src/test/resources/devices/ios.json`.

Пример текущей конфигурации:

``` json
{
  "devices": [
    {
      "udid": "emulator-5554",
      "deviceName": "Pixel 10 Pro XL",
      "platform": "Android",
      "platformVersion": "17",
      "systemPort": 8200
    },
    {
      "udid": "emulator-5556",
      "deviceName": "Pixel 10 Pro",
      "platform": "Android",
      "platformVersion": "17",
      "systemPort": 8201
    }
  ]
}
```

Для каждого параллельно работающего устройства должен быть указан уникальный `systemPort`.

## Запуск тестов

1.  Запустите Appium Server по адресу, указанному в `config.properties`.
2.  Запустите Android-эмуляторы или подключите устройства.
3.  Установите переменные окружения `PLATFORM`, `TEST_LOGIN` и
    `TEST_PASSWORD`.
4.  Запустите тесты из корня проекта:

``` bash
mvn clean test
```

TestNG suite настраивается в `src/test/resources/testng.xml`. В текущей конфигурации используется 
`parallel="methods"` - методы тестов могут выполняться параллельно.

Количество одновременно выполняемых тестов с доступом к устройствам ограничивается количеством устройств 
в `android.json`: если свободных устройств нет, следующий поток ожидает освобождения устройства в`DevicePool`.

## Отчёты Allure

Во время выполнения тестов Allure сохраняет результаты в
`allure-results/`.

Для формирования и просмотра отчёта требуется установленный Allure Commandline.

Просмотр отчёта с локальным веб-сервером:

``` bash
allure serve allure-results
```

Либо можно отдельно сформировать HTML-отчёт:

``` bash
allure generate allure-results --clean -o allure-report
allure open allure-report
```

В отчёт добавляются:

-   результаты выполнения тестов;
-   скриншоты при неуспешных проверках;
-   лог выполнения каждого теста.

## Логирование

Для логирования используется SLF4J с реализацией Logback.

Конфигурация находится в `src/test/resources/logback-test.xml`.
Благодаря `SiftingAppender` для каждого теста создаётся отдельный лог-файл:

``` text
target/logs/<test-id>.log
```

Идентификатор включает имя тестового метода и UUID, поэтому файлы разных запусков не перезаписывают друг друга.

Лог каждого теста прикрепляется к его результату в Allure под названием`Test execution log`.
